## 0 结论先行

1. **现状**：App 完全离线。三项测试由 KMP 共享引擎完成，`ScreeningPlatform.saveRecord` 把整份 JSON 写进本机私有目录；结果页只与本机上一条同病种记录对比。应用没有网络权限、账号、家庭成员或同意记录。`backend/` 只有一个标准库 Python 训练脚本（`screening_model.py`），**它读取的 `research-rules-2` 特征名已与 App 现在写出的 `protocol-9.18-rules-1` 不一致**，需要随第二阶段更新；保留它作为离线训练工具，不作为服务端基础。
2. **后端选型**：Kotlin + Ktor 3 的 API 服务（`backend/server`），PostgreSQL 为生产库、H2 为本机开发与测试库。理由：与客户端共用 `shared/sync` 的数据契约（同一份 kotlinx-serialization DTO），后续可直接在服务端 JVM 复用 `shared/screening` 的规则代码做复算；团队现有技能是 Kotlin；JDK、Gradle 已在本机。Python 继续负责离线训练与评估。
3. **边界**：手机端始终可离线完成测试和规则评估；上传是**可选**的，只有同时满足「已配置服务器地址 + 已登录 + 已授予健康数据处理同意」才会离开设备。发布包默认不配置服务器地址。
4. **智能评估**：规则保留为「安全底线 + 质量门控」，学习模型只作为「经校准的评分器」叠加其上，**不能降低规则给出的风险等级**；任何模型在获得有金标准标签的临床数据前只运行在影子模式。LLM 只做报告解释，不做判定。
5. **需要决策**：托管与地域、短信/微信登录供应商、LLM 供应商或自建、医疗器械注册路径、数据保留期限（§9）。第一阶段没有做出任何花钱或把健康数据发往第三方的选择。

## 1 总体架构

```
┌──────────── 手机（安卓 / iOS）────────────┐          ┌──────────────── 服务端 ────────────────┐
│ feature:services  三项测试（共享引擎）      │          │ Ktor API (backend/server)              │
│   └ ScreeningPlatform.saveRecord ──┐       │          │  ├ auth：账号、令牌轮换                 │
│ core:data                          ▼       │  HTTPS   │  ├ subjects：本人 / 家庭成员            │
│   ScreeningRecordRepository  本机文件 + 发件箱 ──────────▶├ consents：分项同意、版本、撤回         │
│   AccountRepository   令牌（Keystore 加密）│  JSON    │  ├ records：幂等上传、摘要索引、加密原文 │
│   SyncWorker（WorkManager，指数退避）      │          │  ├ history：同病种趋势与对比            │
│ core:network  EyeApiClient（HTTP 端口实现）│          │  ├ export / 删除 / 审计 / 保留期清理    │
│ shared/sync  DTO + RecordSummary + 同步引擎│◀─ 同一份契约 ─▶ shared/sync（JVM）                │
│ shared/screening 规则评估（离线安全底线）  │          │  └ （P2）shared/screening 服务端复算    │
└────────────────────────────────────────────┘          │ PostgreSQL（摘要明文列 + 原文 AES-GCM） │
                                                        │ （P3）模型注册表 / 影子评分 / 标注      │
                                                        │ （P4）报告解释服务（LLM，待选型）        │
                                                        └────────────────────────────────────────┘
```

### 1.1 模块落位（遵循 NIA 规则）

| 位置 | 新增 / 修改 | 理由 |
|---|---|---|
| `shared/sync`（KMP，新） | 传输 DTO、`RecordSummary`（从记录 JSON 抽取病种/版本/风险/特征）、`RecordSyncEngine`（推送策略，端口为 `RecordOutbox`、`RecordRemote`） | 双端共享同步规则与契约；服务端 JVM 也依赖它，避免契约漂移 |
| `core:network`（安卓，新） | `EyeApiClient`：基于 `HttpURLConnection` + kotlinx-serialization 实现 `RecordRemote` 与账号接口 | NIA §9.2「接入云端时新建 core:network」；不引入 Retrofit/OkHttp，接口少、依赖少 |
| `core:data`（安卓） | `AccountRepository`、`ScreeningRecordRepository`（接口 + 实现 + Hilt 绑定同模块）、`SyncWorker` | NIA §5：读返回 Flow、写用 suspend；离线优先，本机文件仍为事实源 |
| `feature:services` | `AndroidScreeningPlatform.saveRecord` 改为经 `ScreeningRecordRepository.save` | 测试流程与记录格式不变 |
| `feature:mine` | 「云端同步与数据」区：登录/注册、分项同意、立即同步、导出、删除云端数据 | 首个使用账号的页面 |
| `backend/server`（新，独立 Gradle 构建） | Ktor 服务、迁移脚本、测试 | 与安卓、共享构建并列，`includeBuild` 共享模块 |
| `backend/screening_model.py` | 保留；P2 更新到当前特征版本 | 离线训练 |

> NIA 差异：同步 Worker 暂放 `core:data/sync`，未单独拆 `sync:work` 模块；出现第二个同步仓库时再拆。

## 2 数据模型

### 2.1 实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `accounts` | id(UUID)、email（唯一，小写）、password_hash（PBKDF2-SHA256，600k 次迭代 + 每户盐）、display_name、created_at、deleted_at | 账号即「监护人/操作者」。P2 增加手机号 + 短信验证码（❓供应商） |
| `subjects` | id、account_id、relation（SELF/CHILD/PARENT/SPOUSE/OTHER）、nickname、birth_year、birth_month、sex、is_default | **被测者**。斜视多由家长替儿童测，记录挂在被测者而非账号上。只存出生年月不存完整生日（最小化） |
| `consents` | account_id、subject_id（可空）、type、policy_version、granted、recorded_at、source | **追加式**，最新一条生效；撤回也是一条记录，保留证据链 |
| `records` | id（客户端生成 UUID，作为幂等键）、account_id、subject_id、kind、protocol_version、assessment_version、risk_level、quality、tested_at、uploaded_at、payload_sha256、summary_json（特征等）、payload_cipher、key_id | 测试记录**不可变**；同 id 不同内容返回 409 |
| `assessments`（P2） | record_id、source（DEVICE_RULES/SERVER_RULES/MODEL）、version、risk_level、output_json、created_at | 同一记录可有多版评估；第一阶段设备端评估存在 records 摘要里 |
| `refresh_tokens`、`access_tokens` | token_hash（SHA-256）、account_id、family_id、expires_at、revoked_at、replaced_by | 只存哈希；刷新令牌轮换，旧令牌被重用则吊销整个家族 |
| `audit_events` | id、at、actor_account_id、action、target_type、target_id、outcome、ip_hash | 只追加；不含健康数据内容 |
| `clinical_labels`（P3） | subject_id、study_id、site、gold_standard_json、labelled_by、labelled_at | 研究点录入的金标准，与手机记录按受试者关联 |
| `models`（P3） | id、kind、input_feature_version、artifact_sha256、training_snapshot、metrics_json、calibration_json、status（SHADOW/ACTIVE/RETIRED） | 模型注册表 |

### 2.2 问卷与测试记录

- 问卷答案已在记录的 `profile` 字段里（键为题目 `key`，例如「年龄」「干眼症状」），**和那次测试一起不可变保存**——它描述测试当时的状态，不另做一张可编辑的问卷表。服务端从原文提取年龄等少量协变量进入摘要。
- 记录格式由 `shared/screening` 定义，同步层**不改动**测试 JSON，而是在外面包一层信封（record id、subject id、tested_at、payload 哈希）。唯一的格式修改：干眼记录补写 `assessmentVersion`（原来缺失，导致无法区分规则版本）。
- 服务端摘要（明文列）：kind、版本、风险、质量、`features` 数值表——用于列表、趋势和对比查询。**原文**（问卷、逐题作答、逐帧眼位序列）整体 AES-256-GCM 加密后存储，只在本人查看、导出、或（经研究同意后）去标识导出时解密。

### 2.3 同意类型

| type | 何时需要 | 缺失时 |
|---|---|---|
| `PRIVACY_POLICY` | 注册 | 不能注册 |
| `HEALTH_DATA_SYNC` | 任何上传 | 上传返回 403，客户端停止同步、本机数据不受影响 |
| `GUARDIAN` | 为未满 14 周岁的被测者上传（按 PIPL，未满 14 周岁的个人信息属敏感个人信息，需监护人同意） | 该被测者的记录返回 403 |
| `RESEARCH_USE` | 去标识数据进入训练 / 研究导出 | 不进入任何训练集；不影响本人使用 |

同意文本版本号随 App 发布；文本更新后客户端提示重新同意。

## 3 API（v1）

全部 JSON；认证用 `Authorization: Bearer <access token>`（不透明令牌，15 分钟）；刷新令牌 30 天、每次轮换。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/auth/register` | email、password、displayName、`privacyPolicyVersion` → 令牌对；自动建「本人」被测者 |
| POST | `/v1/auth/login` | → 令牌对；失败统一提示，按 IP+账号限速 |
| POST | `/v1/auth/refresh` | 轮换；旧令牌重用 → 吊销整个家族并 401 |
| POST | `/v1/auth/logout` | 吊销当前刷新令牌家族 |
| GET / DELETE | `/v1/me` | 账号信息；DELETE 立即硬删除全部被测者、记录、同意、令牌，仅留不含内容的审计 |
| GET | `/v1/me/export` | 全量导出（含解密原文），满足查阅复制权 |
| GET / POST | `/v1/me/consents` | 当前生效状态 / 追加一条授予或撤回 |
| GET / POST | `/v1/subjects` | 列出 / 新建家庭成员 |
| PATCH / DELETE | `/v1/subjects/{id}` | 修改 / 删除成员（连同其记录） |
| PUT | `/v1/records/{id}` | 幂等上传：`{subjectId, testedAt, payload, payloadSha256}`；201 新建、200 重复、409 冲突 |
| GET | `/v1/records?subjectId&kind&limit&before&beforeId` | 摘要列表（不含原文），按（测试时间, id）倒序游标分页 |
| GET / DELETE | `/v1/records/{id}` | 单条（含解密原文）/ 删除 |
| GET | `/v1/subjects/{id}/history?kind=` | 同病种时间序列（风险、质量、关键特征） |
| GET | `/v1/records/{id}/compare` | 与同被测者同病种上一条可评估记录的特征差 |
| GET | `/health` | 存活检查（不连库） |

错误体统一 `{"error": "<代码>", "message": "<中文说明>"}`；代码如 `consent_required`、`conflict`、`invalid_token`。

### 3.1 同步协议

- 客户端在保存时生成 UUID 作为记录 id，写入本机发件箱（状态 `PENDING`）。
- `RecordSyncEngine` 按测试时间顺序逐条 PUT。201/200 → `SYNCED`；409 → `CONFLICT`（不重试，提示）；401 → 刷新一次后仍失败则停止并要求登录；403 `consent_required` → 停止整轮；5xx / 网络错误 → 保持 `PENDING`，由 WorkManager 指数退避重试；4xx 其它 → `REJECTED`（附原因，不重试）。
- 发件箱记录归属账号：换账号或注销后重新注册时，全部本机记录换新编号重新待传。应用启动时若满足条件会补传积压记录。
- 记录不可变，所以没有双向合并问题；多设备拉取（P2）只拉别的设备上传的摘要，原文按需下载。
- 删除：本机删除不自动删云端；云端删除通过「我的」页显式操作。

## 4 安全与隐私

| 关注点 | 第一阶段措施 | 待部署时补齐 |
|---|---|---|
| 传输 | 服务端在生产模式拒绝非 HTTPS 请求（检查 `X-Forwarded-Proto`）；安卓仅调试构建允许明文到本机地址 | 由反向代理终止 TLS 1.2+、HSTS；考虑证书固定 |
| 静态加密 | 原文 AES-256-GCM，AAD 绑定 record id + account id（防挪用密文）；密钥带 key id 便于轮换；密钥来自环境变量，不入库不入仓 | 换为云 KMS 信封加密（❓供应商）；数据库磁盘加密；备份加密 |
| 口令 | PBKDF2-HMAC-SHA256 600,000 次 + 16 字节盐；常量时间比较 | 视供应商改为 Argon2id |
| 令牌 | 随机 256 位，库内只存 SHA-256；刷新令牌轮换与重用检测 | — |
| 手机端令牌 | Android Keystore 中的 AES-GCM 密钥加密后存 SharedPreferences | iOS 用 Keychain（P2） |
| 访问控制 | 每个查询都按 account_id 过滤；越权一律 404 而非 403，不泄露存在性 | 研究人员 / 医生角色（P3）走独立接口与审计 |
| 审计 | 登录、上传、查看原文、导出、删除、同意变更全部记审计；IP 只存加盐哈希 | 审计外送只读存储 |
| 最小化 | 不收姓名、身份证、完整生日、照片或视频；只存出生年月 | 若研究需要视频，单独同意 + 单独存储 |
| 保留 | 账号删除即硬删；可配置记录保留天数（默认不过期）、过期令牌每日清理、审计保留 3 年（可配） | 按研究方案和法规确定（❓） |
| 限速 | 认证接口按 IP 限速 | WAF |
| 日志 | 请求日志不打印请求体、令牌、邮箱 | 集中日志脱敏 |

合规要点（需法务确认 ❓）：健康数据属《个人信息保护法》敏感个人信息，需单独同意与个人信息保护影响评估；未满 14 周岁需监护人同意；境内收集的数据原则上境内存储，**托管地域应在中国大陆**；文档引用的《健康医疗数据安全指南》（GB/T 39725）要求的分级、去标识与审计在本设计中对应 §2、§4。

## 5 智能评估与诊断系统

### 5.1 现状评估

- 规则写死在 `ScreeningAssessment.kt`（老视、斜视）、`DryEyeProtocol.kt`（`DryEyeAssessment`）、`StrabismusGaze.kt`（注视监督），阈值来自文档的经验值（如 10Δ / 5Δ / 6Δ、BSI 0.7/0.5、眨眼 10–16 次、VMR 0.85、15−0.25×年龄），**未经本设备或临床队列验证**。
- 已有的好做法要保留：质量不足就拒判（UNKNOWN 不当作低风险）、结果用语为「初筛参考」、特征表随记录保存、`modelVersion` 标识规则版本。
- 缺口：干眼记录没有规则版本；质量只有「合格/不足」两档，没有连续的可信度；规则无法表达不确定性；没有跨次的个人基线；没有标注数据通道。

### 5.2 分层管线

```
L0 采集质量   帧级：人脸/虹膜置信度、头姿、距离、光照、映光点检出（已有，逐帧写入）
L1 特征提取   shared/screening 确定性计算（已有），带 featureVersion
L2 规则       质量门控（拒判） + 红旗规则（安全底线） + 现有分级  ← 离线、可解释、永远运行
L3 模型评分   每病种一个经校准的风险概率 p（先表格模型，后时序模型）  ← 需临床标签
L4 不确定性   保形预测集 / 质量加权 → {确定, 临界→延长测试, 不可信→重测}
L5 合成策略   最终等级 = max(规则底线, 模型等级)；模型永不下调规则
L6 解释       模板报告（现有） → LLM 改写（P4，受限生成 + 校验）
```

**合成策略细则（L5）**

1. L2 质量门控失败 → UNKNOWN，模型不运行。
2. 红旗规则（如注视稳定且水平 ≥10Δ）命中 → 至少「高度疑似 / 建议就医」，模型不能下调。
3. 模型只在 `ACTIVE` 状态、输入特征版本匹配、样本在训练分布内（特征越界检测）时参与；否则退回纯规则并在报告注明。
4. 模型输出的保形预测集若同时含「低」与「高」→ 显示「结果不确定」并建议延长测试（干眼已有延长入口）或复测，而不是给出居中等级。
5. 报告同时展示规则依据与模型依据，用户可见「本结论由规则 X 版 + 模型 Y 版生成」。

### 5.3 各病种模型路线

| 病种 | 第一批模型（表格） | 后续模型（时序/多模态） | 金标准标签 |
|---|---|---|---|
| 干眼 | 逻辑回归 / 单调约束 GBM：眨眼频率、最长睁眼、VMR、下降时间、眨眼前后正确率、症状、年龄、隐形眼镜、屏幕时长；**单调约束**体现文档要求的「临床知识约束」（如 VMR 越低风险不降） | 文档的「眨眼事件驱动」模型：以眨眼间期为片段编码视标应答 + 反应时 + 眼睑特征，质量权重 × 时序注意力；多任务（干眼风险、泪膜稳定性、症状严重度、可信度） | 现行干眼诊疗共识的诊断结论 + NIBUT/TBUT、Schirmer、OSDI、睑板腺评估 |
| 老视 | 年龄条件化的调节幅度、近视力、灵敏度、离焦曲线 → 「调节年龄」回归 + 老视风险分类；标准 / 日常两模式分开建模 | 移近过程的距离—时间曲线、反应时序列 | 临床推进法/负镜片法调节幅度、反转拍灵敏度、近附加、验光 |
| 斜视 | GBM（文档建议 LightGBM/CatBoost）或贝叶斯层次模型（小样本）：HDE/VDE 及稳定度、再注视幅度/速度/残余、BSI 及分量、年龄、质量率；输出风险 + 连续棱镜度回归 | 直接从 `eyeSamples` 序列学习（1D CNN/Transformer），替代人工映光点几何；在设备端用更好的眼部关键点模型 | 三棱镜交替遮盖（Δ）、遮盖-去遮盖、同视机、立体视（Randot/Titmus，文档写法待核对） |

**评估要求（与文档 §4 一致）**：按受试者划分训练/验证/测试；跨设备、跨年龄组（3–5/6–8/9–12 岁）分层报告；ROC/AUC、敏感度/特异度在预设操作点、校准曲线与 Brier 分数、决策曲线；重测信度（ICC/加权 Kappa）；独立外部验证后才可转 ACTIVE。防止标签泄漏：临床检查结果只能做标签，**不能**作为模型输入（手机自测时不存在）。

### 5.4 LLM 辅助报告

- 输入只含结构化结果（风险等级、触发的规则/特征贡献、质量、年龄段、病种）与**经审核的知识库片段**；不发送原始序列、问卷全文或身份信息。
- 输出受限：固定章节（结论、异常指标、就医建议、家庭观察要点）；后置校验：不得出现诊断性措辞（「确诊」「患有」）、不得出现输入中没有的数值、必须包含「初筛参考，不能替代眼科诊断」；校验失败回退到现有模板报告。
- 部署：❓托管国内大模型 API、私有部署开源模型，还是暂不启用。任何一种都意味着结构化健康数据离开本服务，需要单独同意与数据处理协议。**第一阶段不实现 LLM 调用。**

### 5.5 现在可以上线 vs 需要临床数据

| 现在可以做（不需要标签） | 需要有标签的临床数据 |
|---|---|
| 规则版本化（含干眼补版本号）、规则配置化与回归测试 | 任何「概率」「敏感度/特异度」对外表述 |
| 连续质量分（帧级置信度聚合）与拒判理由 | 替换文档经验阈值（10Δ、6Δ、BSI 0.7/0.5、VMR 0.85、3 次/分） |
| 个人基线与趋势：同一被测者多次测试的变化，按实测重测变异判断「变化是否超出测量误差」（先用保守的经验区间，P3 用重测研究的 ICC/SEM 替换） | 年龄常模（儿童眼位、调节年龄） |
| 服务端存储特征与原始序列、去标识研究导出、标注录入通道 | 模型训练、校准、保形预测的校准集 |
| 模型注册表 + 影子模式（只记分不展示） | 模型转为 ACTIVE、模型参与展示 |
| 模板化通俗报告 | LLM 报告的临床内容审核 |
