# newpart 代码对比与整合建议

评估日期：2026-10-20。范围：`newpart/EyeProject`、`newpart/EyeProjectBackend` 与当前主工程的干眼、资料、记录和后端实现。

本次是代码评估，未合并业务代码。结论来自实际源码；随附项目的 README 有滞后，例如后端 README 仍称只有注册登录，但实际已经实现健康档案和干眼记录接口。

## 1. 结论

**可以参考，而且有明确可用的改进点；建议以当前主工程为基础，按功能吸收，不整体替换干眼模块或后端。**

优先参考：历史详情展示、数据质量原因的结构化表达、视标呈现回调、眨眼后应答变化的描述性分析。OCEC 模型接入方式可用于后续对照实验。详细健康档案可以按实际需求逐步扩展。

保留当前的三病种共用架构、家庭成员归属、离线保存和同步、评估版本与原始报告、质量不足拒判规则。两份工程的视标数值含义和测试时序不同，无法直接拼接算法或历史数据。

## 2. 功能对比

| 方面 | 同学工程 | 当前主工程 | 整合判断 |
|---|---|---|---|
| 客户端结构 | Android，干眼编排主要在 ViewModel | Android/iOS 共用 `shared/screening` 引擎 | 新规则继续放共享层；不能直接搬整个 ViewModel |
| 干眼流程 | 可跳过练习；两正式段之间倒计时；每段重置阶梯 | 练习后保留基线，60 秒自然眨眼连续进入 20 秒睁眼；支持延长、休息复测 | 保留当前流程，协议差异交老师确认后再变更 |
| 视标定义 | 自定义 0.0–1.0 档位，越大视标越大，固定 40 cm 几何 | 小数视力档位，越大视标越小，按距离换算并检查像素能力 | 不同物理含义，禁止直接对照 level 数值 |
| 眨眼输入 | OCEC 双眼睁眼概率均值，阈值 0.5，连续 3 帧闭眼 | EAR 自适应阈值、闭眼时长判定、低帧率证据不可用 | OCEC 先作为并行观测，不立即替换 |
| 风险分析 | 20 秒段前后半档位/反应时变化，加佐证分 | `rules-2`：质量门控、视力变化模型、眨眼与症状证据族、测量不确定性 | 可借统计项，暂不迁移分数与阈值 |
| 质量说明 | 距离、亮度、环境光、作答样本及依从性原因 | 完整性、有效帧、距离、头姿、分析帧率、未作答比例等 | 借鉴分项说明，保留当前拒判门控 |
| 记录 | 主动上传；本地不保留副本；有历史列表、详情、逐条删除 | 本机自动保存、摘要列表与导出、同步发件箱；服务端有列表/详情/删除/趋势/对比 | 优先补当前客户端的完整详情和云端查询入口 |
| 健康资料 | 左右眼视力/验光、用药和隐形眼镜时间范围、病史列表等结构化字段 | 家庭成员资料、三病种问卷共用、资料同步 | 按成员扩展字段，避免只挂账号导致家人资料混在一起 |
| 后端 | FastAPI + MySQL，JWT，JSON 文件 + 数据库摘要 | Ktor，开发 H2/生产 PostgreSQL 配置，原文加密入库、同意、令牌轮换、审计 | 保留现有服务作为统一入口 |

## 3. 最值得吸收的部分

### 3.1 历史详情与报告复用（优先）

同学工程的 `DryEyeHistoryScreen`、`DryEyeDetailViewModel`、`core/ui/dryeye/DryEyeResultContent.kt` 已形成“列表 → 详情 → 复用报告组件”的路径，区分加载失败、记录不存在、空列表，并提供逐条删除。

我们已有 `feature/mine/LocalRecordsSheet.kt`，能查看摘要和导出；服务端 `RecordService` 已有列表、详情、趋势与对比。不过 Android 的 `EyeNetworkDataSource` 还没有暴露这些记录查询接口，现有本机列表也不是完整报告详情。

建议补齐记录查询仓储和独立详情入口，沿用现有三病种 `ResultReport` 展示内容和设计令牌。先让本机记录可打开完整报告，再接云端分页查询，最后增加同成员、同病种的趋势和对比。

**不要照搬其“打开旧记录就用最新算法重算并替换显示”的行为。** 同学的 `DryEyeDetailViewModel.load()` 每次调用当前 `DryEyeAnalyzer.analyze()`，旧结论可能随应用更新而改变。当前工程已保存 `assessmentVersion`、证据和特征，应默认展示当时报告；需要新版复算时，单独显示版本和结果，保留原结论。

### 3.2 视标呈现与计时分离（优先）

同学的 `OptotypeTask.next()` 生成视标，`markPresented()` 才开始计时；`OptotypeView` 用 `presentationId` 和 `withFrameNanos` 回调，未呈现前拒绝作答和超时。

当前 `DryEyeEngine.trialLoop()` 在更新 UI 状态之前记 `onset`，超时也随即开始。界面调度延迟会进入反应时，卡顿时更明显。

建议借鉴呈现确认机制：共享引擎生成题目编号，Android/iOS 各自回报对应题目的呈现时间，忽略旧编号和重复回调，再启动答题计时。计时使用单调钟，记录另存墙钟/相对时间。`withFrameNanos` 是帧同步信号，并非屏幕实际发光时间的硬件测量，不能宣称毫秒级显示精度。

### 3.3 数据可靠性与描述性指标（优先）

同学的 `DryEyeAnalysis`、`DryEyeQualityReason`、`DryEyeAnalyzer.quality()` 把统计量、风险和数据可靠性分开，质量原因带维度、实测值、阈值和严重程度，适合解释“为什么本次数据不可靠”。

可补充距离标准差、按阶段的超时/主动看不清次数、睁眼阶段眨眼次数，以及“距上次眨眼 0–1、1–2、2–3、3–4、≥4 秒”的应答分箱。当前已有眨眼前后两秒正确率，分箱可以提供更细的描述。空箱必须标记无数据，不能绘制成零。

需要调整后再用：

- 同学的风险与质量分别计算，距离等质量失败仍可能保留一个风险分；我们继续在质量不足时拒绝给结论。
- 同学把“看不清”和超时合并为无效作答；我们目前识别连续超时段。主动看不清、答错、超时应分别记录，如何进入评估另行定义，不直接照搬 30% 和每段至少 8 题等候选阈值。
- 同学的 `intervalBins()` 平均反应时包含超时和看不清，而主评分排除了它们。借用时统一统计口径，并显示样本数。
- 我们测试期间窗口亮度已设为最高，不能直接拿系统亮度读数代替实际窗口亮度；环境光读不到也应与零照度区分。

### 3.4 OCEC 模型接入（先验证）

同学新增 `core:vision`，将 `OcecEyeGeometry` 和 `OcecEyeOpennessClassifier` 接到相机回调，输出 `EyeLandmarks.openness`，同时保存 EAR 和概率，便于离线对照。

本次比较模型文件的 SHA-256：同学 `core/vision/.../ocec_p_float32.tflite` 与我们 `feature/testmodel/.../ocec_p.tflite` **字节一致**：

`ac5c52e30e97e135c5819ffb1402c5e28ef53c72d740da97e0727e4c17455f3d`

所以新增价值主要是生产测试链路的模块化接入，不是提供了另一套新训练模型。

其 `VISION.md` 明确注明裁剪比例未标定、分辨率与已有实验不同、戴镜场景需核验。连续 3 帧判闭眼也受帧率影响。建议先并行保存 EAR/概率，记录有效分析帧率和推理耗时，按人工标注的眨眼事件比较漏检/误检，再决定是否切换。若采用，保留时长判定、不可用状态和质量门控，并验证 iOS 的等价输入与推理流程。

### 3.5 详细健康档案（后续）

`HealthDetails`、`Measurement` 和病史子表支持左右眼裸眼/矫正视力、球镜/柱镜/轴位、眼部用药、手术、过敏、隐形眼镜史、家族史，比当前问卷粒度细。

建议先选确实参与测试解释或老师要求的字段，挂在现有被测者上。保留当前必填项判断和测试时资料快照；不要直接把数字枚举转成现有中文字符串，也不要覆盖已有成员资料。需要新增共享字段模型、旧资料迁移和两端表单后再接同步。

## 4. 不适合直接迁入的实现

### 4.1 自定义风险分和视标体系

`OptotypeGeometry` 明确说明档位不是视力值；同学 `DryEyeThresholds` 也明确说明阈值是草拟值、缺少阳性样本锚点。当前规则同样有待验证，但不能据此认为替换为 0–100 分就更准确。

如果老师希望保留两套方案，应将其作为独立协议和评估版本，清楚记录档位定义、尺寸、距离、设备和时序，不把不同协议放进同一趋势直接比较。

### 4.2 仅远端保存

`RemoteDryEyeRepository` 明确只有远端；ViewModel 只把完成会话保存在内存里等待用户点击上传。网络失败或离开页面后存在丢失风险。继续使用当前自动本地保存、分项同意后同步的机制。

### 4.3 直接更换后端或只改 Base URL

| 契约 | 同学后端 | 当前后端 |
|---|---|---|
| 账号 | 手机号 + 密码，JWT | 邮箱 + 密码，访问/刷新令牌与轮换 |
| 响应 | `{code,message,data}`，业务错误 HTTP 200 | 正常 HTTP 状态与 `{error,message}` 错误体 |
| 记录上传 | `POST /dry-eye/sessions`，同编号覆盖 | `PUT /v1/records/{UUID}`，相同内容幂等，不同内容 409 |
| 归属 | 按账号/用户 | 按账号下的被测者 |
| 原始内容 | 明文 JSON 文件 + 表中元数据 | 加密原文与摘要在数据库事务中保存 |
| 生命周期 | 当前主要是账号登录、档案、干眼记录 | 三病种记录、同意、家庭成员、导出、注销、审计 |

因此不能直接换服务器地址。推荐维持当前契约，吸收查询展示和结构化字段。如果以后明确要求部署同学的 FastAPI 服务，需要单独制定适配和迁移方案，保证身份、成员、记录编号、错误语义和旧数据的映射。

同学后端并非可视化管理后台：本次检查到的是 API、数据库和 Swagger 文档，没有看到管理端 Web 界面。老师所说的数据后台若包含医生工作台、标签录入或统计管理，仍需另外确认范围。

## 5. 实际发现的存储问题

### 5.1 同编号并发保存可互相覆盖临时文件（已隔离复现）

位置：`newpart/EyeProjectBackend/app/storage.py` 的 `save_session()`。

两个请求写同一会话时都使用 `<session>.json.tmp`。即使最终用 `os.replace()` 原子替换，共用临时路径仍会竞争：一个请求可能把另一个请求写入的内容改名，另一个请求随后因临时文件已消失而失败。成功请求返回的哈希也可能与实际文件不符。

本次直接加载该存储模块，使用临时目录和两个线程，以屏障控制交错顺序；仅替换配置和重命名调度，不连接数据库。结果：

```text
请求 A：save_session 返回成功
请求 B：FileNotFoundError
A 返回的 digest 与落盘文件 SHA-256：不一致
```

若迁入这种存储方式，至少需要每次写入独立临时文件；但这还不能解决数据库摘要与内容跨请求错配，仍需同会话串行化、版本检查或不可变对象键设计。

### 5.2 数据库和文件不是同一事务（源码确认）

位置：`app/routers/dry_eye.py:save_session()`。文件先覆盖、数据库后提交；源码已注明覆盖写库失败会留下旧摘要与新文件不一致。删除与上传交错也需要处理。因此不建议用该方式替换当前事务内写入加密原文的实现。

### 5.3 验证与查询仍需补强（源码确认）

- `DryEyeSessionUpload` 的完整会话是开放 `dict`；一致性校验主要检查 sessionId 和结束早于开始，未完整校验元数据统计与原文相符。客户端摘要不能直接作为研究真值。
- 列表接口用 `.all()` 一次取全部会话，没有分页。当前后端已支持游标分页，应继续使用。
- 当前请求体上限按 Content-Length 判断，源码注明分块传输可绕过，需要部署层/实际读取上限共同约束。

这些是具体迁入风险，不代表本次已完成整个后端的安全审计。

## 6. 建议实施顺序与验收

1. **记录体验**：本机完整详情、原报告复用、阶段作答统计与质量原因。验收：离线可看；旧结论和版本保持；三病种风格统一；无数据不会显示零风险。
2. **测量细节**：视标呈现回调、主动看不清与超时分开、描述性分箱。验收：旧题回调/重复作答被忽略；卡顿不提前消耗答题时长；跨阶段计时正确；Android/iOS 共享规则一致。
3. **云端记录入口**：扩展现有 network/data 接口，连接列表、详情、删除、趋势和对比。验收：按成员过滤、游标分页、无同意不上传、令牌过期处理和离线回退。
4. **OCEC 对照实验**：使用现有实验模块或独立可关闭的采集入口对比。验收：相同视频/设备、人工事件标注、戴镜/弱光/低帧率分组、误检漏检及推理耗时记录。确认后再进入正式流程。
5. **资料扩展**：按老师确定的字段逐项增加共享模型、迁移和表单；不先迁入整套账号/数据库。

可交给另一位同学独立完成的工作：OCEC 裁剪与事件标注验证；健康档案字段映射表；FastAPI 存储并发修复与独立测试库；当前后端记录查询的契约测试。先约定输入输出，避免直接改两份工程的同一个主流程。
