# 眼科视角系统测试与建议

日期：2026-09-25。对象：当前工作区版本，包含已有未提交改动。

本报告按眼科临床流程审视软件，不代表执业医师签署的临床验证结论。此次没有连接 Android 真机，未进行患者测试、相机精度实测或界面视觉验收。发现分为自动化测试结果、源码可确认缺陷、需要真机或临床验证的风险。未修改业务代码。

## 结论

当前适合继续作为研究原型；尚不适合向患者提供可据以排除干眼、老视或斜视的结论。优先处理干眼流程和医学解释，其次补齐老视、斜视的边界判读，再开展真实受试者验证。

值得保留的设计：老视屏幕/距离标定、单眼及双眼任务、视标分辨率限制；斜视光学点不足时拒绝评估；模型训练按受试者划分留出集，文档明确研究分数不等于诊断概率。

## 优先修复：影响结果可信度或基本使用

### 1. 干眼结果把眨眼次数解释为泪膜维持能力（高优先级）

源码确认：`DryEyeScreen.kt:321` 显示“保持睁眼期间的眨眼次数越少，泪膜维持能力越好”。该测试没有直接观测泪膜破裂；眨眼次数还受配合、感觉、注意力和漏检影响。仅此指标不足以支撑上述结论。现有“健康参考”声明不能消除具体解释的误导。

建议：改为“本次记录睁眼任务中的眨眼次数，不能据此判断泪膜稳定性或排除干眼”；将入口说明为眨眼行为观察/研究测试。若开展干眼筛查，应由临床团队制定症状问卷与客观眼表检查对照方案。干眼诊断需要结合症状和眼表稳态相关检查，参见 [TFOS 诊断方法报告](https://tfosdewsreport.org/report-diagnostic_methodology/131_36/en/)。

验收：零眨眼、频繁眨眼、相机失效三种情况均不能自动得出“泪膜好/无干眼”；检测中提供“不适，结束测试”，允许自然眨眼，不鼓励忍受疼痛。

### 2. 干眼采样时 UI 仍处于倒计时（高优先级，源码确认）

位置：`DryEyeTestViewModel.kt:135,162,203`；`DryEyeScreen.kt:110` 附近的阶段分支。

`runCountdown` 将公开 UI 状态设置为 Countdown；正式阶段只改变内部 `currentPhase`，未将 `_uiState.phase` 改为 Blink60/Open20。虽然循环继续更新秒数和统计，界面仍走倒计时分支，正式进度与实时眨眼计数界面无法按预期呈现。

建议：阶段切换同步更新公开 UI 状态；添加状态序列测试。验收完整序列：Setup → Countdown → Blink60 → Countdown → Open20 → Result，界面指令与采样阶段一致。

### 3. 干眼“重新检测”无法再次启动（高优先级，源码确认）

位置：`DryEyeTestViewModel.kt:94–103`。

`startTest` 在 `testJob != null` 时直接返回，而完成和 `backToSetup` 均未清空该引用。取消/完成的 Job 仍非空，回到准备页后即使门禁通过，也无法开始第二次检测。

建议：按任务是否活动判断，并在取消/完成时正确重置。验收同一页面连续做三次，以及中途退出再进；每次数据独立。

### 4. 干眼开始后缺少持续质控（高优先级，源码确认）

位置：`DryEyeTestViewModel.kt:137–184,236–247`。

双眼/距离门禁只在 Setup 检查。正式阶段即使失去人脸或相机不再产出有效数据，计时仍会结束并给结果；无脸时可记录 0 cm，断帧时还可能沿用旧距离。与第 1 项叠加后，检测不到眨眼可能被解释为好结果。

建议：记录有效观测时长、最后帧时间、双眼质量、距离合格比例；断帧/失跟踪时暂停或判定无效。零事件必须区分“有效观察中未发生”和“未成功观察”。验收开始后遮挡镜头、移出画面、距离过近、锁屏、撤销相机权限，均不能生成可信的零眨眼结果。

### 5. 准备/倒计时眨眼可能进入正式统计（高优先级，源码确认）

位置：`DryEyeTestViewModel.kt:116,142–144,169–171`；`DryEyeScreen.kt:362` 附近的图表分桶。

检测器准备阶段已运行；`lastSeenBlink` 从 0 开始，但 `lastBlinkElapsed` 没有按阶段清空或过滤。最近一次眨眼若在阶段起点之前，会形成负相对时间并进入事件列表；图表又把负时间归入第一个桶。第二阶段倒计时也有类似问题。

建议：只接收正式阶段时间区间内的事件，使用事件队列避免单个“最近事件”变量覆盖事件。验收在倒计时末眨眼、正式期完全不眨眼，正式期计数应为零且不存在负时间。

### 6. 老视“所有视标都未通过”未必触发近视力异常提示（高优先级，源码推导）

位置：`ScreeningAssessment.kt:29–34,60–76`。

视力阈值只取通过等级，所有等级失败时为 null；质量门禁仅要求每眼至少四题。异常判断又要求 `both != null && both < 0.5`。因此在近点与远近切换未触发其他提示时，双眼所有等级均未通过仍可得到“本次未触发预设表现提示”。

建议：明确区分未测试、像素受限、所有等级未通过和有可报告阈值；对有效测试中最低等级未通过给出视功能复核提示，不自行诊断老视。另应呈现单眼下降及双眼差异，避免只由双眼最高通过等级决定提示。

待加测试：三眼条件各等级全错、单眼全错/双眼通过、像素受限、最低等级未通过；全错不能走无提示分支。

### 7. 斜视追随“没有可分析运动”可能被当作完成（高优先级，源码推导）

位置：`ScreeningAssessment.kt:108–142,154–156`。

追随质控只要求相邻帧数；双眼位置恒定时相关系数为 null，但不会因此拒判，且 `pursuitSignal` 为 false。若其余任务无异常，可输出未触发提示及“三任务可用”。没有可测运动不能等同于追随正常。

建议：检查实际运动幅度、水平/垂直任务覆盖、眼动与目标运动的关系；没有足够动态信号输出“追随无法评估”。当前提示主要采用水平量，不能据此排除垂直或其他类型斜视。

待加测试：恒定位置、仅噪声、只采到一种运动方向、双眼同步但完全不跟目标。临床斜视检查包含反光、遮盖和棱镜等不同方法，不能用单一手机眼动相关性替代，参见 [AAPOS 斜视测量](https://www.aapos.org/glossary/strabismus-measurements)。

## 下一批改进

### 8. 同一份老视报告的统计口径不一致（中优先级，源码确认）

`ScreeningMetrics.kt:14–18` 对偶数有效近点取上中位数；`ScreeningAssessment.kt` 的 median 取中间两数平均。例如两次有效值 43、45 cm，统计页为 45 cm，评估特征为 44 cm；MAD 与近似调节需求也可能不同。三次测量中一次无效时即可遇到。建议共用统计函数，并覆盖奇数、偶数和删失数据。

### 9. 疲劳个体化使用默认画像（中优先级，源码确认）

`FatigueMonitor.kt:217` 每次传 `UserProfile()`；`UserProfile.kt:8` 起默认年龄 30、无近视/干眼、主观不适 0。建议未填写显示“未知”，不要等同“没有疾病/不适”；明确评分是行为提醒指数，不能表示疾病概率。老视问卷字段不代表已经接入此疲劳画像。

### 10. 相机占用与遮盖时序需要专项真机验证

干眼 `startMonitoring` 在 `cameraController.isRunning` 时直接返回，没有注册共享帧观察者；先开启后台监测再进干眼页时，可能无法更新门禁。干眼退出还直接调用共享相机的 `stop()`。建议按相机所有权/观察者协议统一接入，测试后台监测→干眼→返回的完整流程。

斜视解除遮盖以用户点击时间为起点，取之后 500 ms 的首尾变化。若先移开遮盖后点击，快速再注视可能已经结束，产生漏记。建议保留点击前后的帧缓冲并记录时序不确定性，结合人工标注评估，而非调整阈值掩盖问题。

仓库旧记录 `docs/真机测试-2026-09-24.md` 曾报告某机型光学有效帧为 0、不能标定。这里只是引用既有记录，本轮未复现。保留拒判机制；先确认受控光源及瞳孔/反光候选点真实性，不应放宽质量阈值换取“通过”。

## 面向患者的流程建议

- 测试前增加症状分流：突发复视、突发视力下降、明显眼痛等不应继续普通自测，应提示及时就诊；复视伴严重头痛、瞳孔异常或头伤需急诊评估。参见 [NHS 复视分流](https://www.nhs.uk/symptoms/double-vision/) 和 [眼科急诊适应情形](https://www.uhbristol.nhs.uk/patients-and-visitors/your-hospitals/bristol-eye-hospital/what-we-do/emergency-care/)。
- 结果首页按“能否解释本次数据 → 观察到什么 → 下一步做什么”呈现。将工程帧数、虹膜直径归一化差等放入医生/研究详情。保留清晰的“不足以排除疾病”边界，但不能用它代替正确异常判读。
- 明确适用人群和矫正条件：目前年龄允许 3–120 岁，斜视结果却统一写儿童流程；需区分成人、儿童和协助者指引。标准模式与“近用 Add 有”的冲突应阻止或要求更正。
- 斜视反光刺激和老视标准化显示分别设定方案，不能把屏幕亮度 100% 当作实测亮度。评估强光不适、大字体、语音、按钮可达性；保留标准化条件记录。
- 结果应能经用户主动操作导出给医生，并支持删除记录。当前仅显示应用私有目录路径，对患者和医生都不便使用。

## 建议的下一轮验收

先完成软件回归：三次连续干眼检测、倒计时边界、失跟踪、后台切换、相机竞争、全错视标、无追随运动、偶数近点统计。每项记录版本、输入、预期、实际和证据，不使用真实患者数据替代合成异常输入。

随后在知情同意下开展受控真机可用性测试：不同年龄/戴镜状态/机型，记录流程完成率、耗时、有效帧率、拒判原因和重复测量差异。真实尺量及受试者实际回答不能由自动化伪造。

最后按病种分别开展临床对照：干眼与症状及眼表检查对照；老视与屈光矫正、标准近视力和临床调节评估对照；斜视与专科遮盖/棱镜检查对照。锁定协议、明确目标病种、按受试者划分数据，报告敏感度/特异度及置信区间，同时报告拒判率、重复性和跨设备差异。样本量应由目标性能与统计方案决定，后端每类五人的运行门槛不代表临床样本量充分。
