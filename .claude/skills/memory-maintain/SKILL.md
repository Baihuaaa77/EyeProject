# auto memory 定期维护

记忆目录由 settings 的 `autoMemoryDirectory` 指定（当前为项目根 `memory/`）。维护遵循 `memory-discipline.md` 的 7 条纪律；**本次维护删除的任何内容都会在汇报中留全文引文**，需要时可手动恢复。

## 流程

### 第一步：全量盘点（只读，不动任何文件）

1. 列出记忆目录全部文件，逐个通读（含 MEMORY.md）
2. `wc -l -c` 记录 MEMORY.md 与每个文件的行数/字节数
3. 对记忆中提到的文件路径、配置、命令抽查仓库现状（判断「过时项」的依据）

### 第二步：逐项体检（对照 10 项检查单）

1. **重复合并**：跨文件的重复或同主题内容 → 合并进最完整的一份，删除冗余份，MEMORY.md 索引去重
2. **冲突修正**：互相矛盾的结论 → 以**有证据、时间更新**的为准改写旧记录，注明证据来源；没有证据支撑谁对谁错 → 双双降级进待确认清单
3. **删除已确认错误**：被仓库现状或新证据直接证伪的内容 → 删除（须确凿；"可能错了"不算确凿）
4. **删除彻底过时**：已完成许久且无复盘价值、或指向已不存在的事物且不含教训价值的内容 → 删除；价值判断拿不准 → 进待确认清单
5. **合并碎片**：多个小文件同属一个主题 → 合并为一个单主题文件，索引同步
6. **拆分多主题**：一个文件装了几个互不相关的主题 → 拆成单主题文件，索引同步
7. **仓库重复排查**：内容在 git 历史、代码、CLAUDE.md、模块文档中明确存在且容易重新获得 → 从记忆中删除该部分（纪律第 6 条）
8. **敏感信息扫描**：密码、密钥、Token、Cookie、私钥、内网地址等凭据类信息 → **立即删除**，并在汇报中提醒用户轮换泄露的凭据
9. **索引格式**：MEMORY.md 仍然一行一个主题，无正文堆放、无失效链接
10. **容量**：对照 150 行/20KB 软上限与 200 行/25KB 硬上限，报告 MEMORY.md 与各文件的余量

### 第三步：待确认清单（删除闸门）

价值判断类拿不准的（如「某条踩坑记录是否还有参考价值」「某条结论是否还算当前有效」）→ **单独列出，每条附「删除理由 vs 保留理由」，问用户后再动。绝不自行删除拿不准的内容。**

### 第四步：执行与汇报

- 合并 / 修正 / 拆分 / 索引整理：直接执行
- 删除：仅执行「确凿错误 / 彻底过时 / 敏感信息」三档；其余走待确认清单

## 汇报格式（固定五段）

1. **合并了什么**
2. **更新了什么**
3. **删除了什么**（每条附引文备恢复）
4. **哪些内容等待用户确认**（附删除理由 vs 保留理由）
5. **MEMORY.md 当前行数和大小**（附各文件容量表 + 距硬上限余量）
